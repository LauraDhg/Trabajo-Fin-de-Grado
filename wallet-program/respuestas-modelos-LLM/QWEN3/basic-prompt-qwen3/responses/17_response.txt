Function "process_instruction":
- Parses instruction data into an InstructionFormat enum using unpack.
- Routes execution to one of four functions based on the instruction type.
- Does not validate account ownership or authority before delegating to handler functions.
- Relies entirely on downstream functions for security checks.

Function "initialize_wallet_account":
- Derives a PDA using "wallet" seed and user_account public key.
- Validates that the provided wallet_account matches the derived PDA.
- Checks if wallet_account has zero lamports to prevent re-initialization.
- Creates a new wallet account via CPI to the system program with signed seeds.
- Serializes a new Wallet struct (amount: 0, initialized: true) into the account data.
- Does not verify that system_program is the actual Solana system program.
- Does not check that user_account is a signer, allowing unauthorized account creation.
- Uses unchecked lamports check (could be manipulated if account is already funded).
- Potential race condition: lamports check and creation are not atomic with initialization.

Function "deposit_amount":
- Derives expected PDA and validates wallet_account matches it.
- Deserializes wallet data using try_from_slice, which checks length.
- Verifies wallet is initialized.
- Uses checked_add to prevent overflow.
- Serializes updated wallet data back to account.
- Does not validate that user_account is a signer, allowing unauthorized deposits.
- No validation that funds are actually transferred; assumes external payment.

Function "withdraw_amount":
- Derives PDA and validates src wallet account.
- Deserializes wallet and checks initialization.
- Validates sufficient balance before withdrawal.
- Uses checked_sub to prevent underflow.
- Serializes updated amount.
- Does not enforce user_account as a signer, enabling unauthorized withdrawals.
- No withdrawal limits or rate limiting.
- No check that lamports in the account match the data balance (decoupling risk).

Function "transfer_amount":
- Derives PDAs for both source and destination wallets.
- Validates both accounts match expected PDAs.
- Deserializes both wallets and checks initialization.
- Checks source has sufficient balance before transfer.
- Updates both balances using checked arithmetic.
- Serializes both accounts back.
- Does not require source user_account or destination user_account to be signers.
- Allows unauthorized transfers if attacker provides correct PDAs.
- Order of balance update is correct (check before subtract), but no reentrancy protection.
- No validation of destination wallet existence or ownership beyond PDA match.
