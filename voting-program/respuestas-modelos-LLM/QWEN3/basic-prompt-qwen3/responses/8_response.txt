Function "vault_program_id":
- Returns a hardcoded Pubkey derived from the string "6dVLkpmd5BvVQF7oXpipnQFtKwba2uQkMMwzHnaqf8Gr".
- This function does not validate or parameterize the program ID, making it a potential risk if the Vault program changes.

Function "action_as_str":
- Maps a u8 action code to a static string for logging purposes.
- Only supports 0, 1, 2, and defaults to "Unknown" for others.
- No security implications, but could mislead logs if invalid codes are passed.

Function "send_create_vault_transaction":
- Constructs and invokes a CPI (Cross-Program Invocation) to create a vault via the Vault program.
- Uses `invoke_signed` with a PDA derived from "vault" and a bump seed.
- Accepts arbitrary `variant_instr`, `id_pubkey`, and `vault_bump` without validation.
- Does not verify that `vault_program` matches the expected Vault program before CPI.
- Risk: If `vault_program` is not validated, attacker could redirect CPI to a malicious program.

Function "send_instr_to_vault_transaction":
- Sends a CPI to the Vault program for deposit or withdraw actions.
- Uses `invoke_signed` with PDA signing via "vault" and bump.
- Data includes `variant_instr`, `amount`, and `id_pubkey`.
- No validation of `variant_instr` within the function; assumes caller checks.
- Risk: If `variant_instr` is untrusted or unchecked, could trigger unintended Vault actions.

Function "process_instruction":
- Entrypoint function that dispatches instructions based on unpacked `InstructionFormat`.
- Relies on `InstructionFormat::unpack` to parse instruction data.
- Each variant calls a corresponding handler function.
- No instruction-level authorization or access control within this function; relies on individual handlers.
- Risk: If `InstructionFormat::unpack` fails to validate data, could lead to memory issues or incorrect dispatch.

Function "create_admin":
- Initializes a new admin PDA account with `admin_bump`.
- Checks that `admin_payer` is a signer and account is uninitialized.
- Uses `create_program_address` with seed "admin" and bump.
- Serializes `Admin_Account` after CPI.
- Risk: Does not verify that `clock_sysvar` is actually the Clock sysvar beyond key comparison; could be spoofed if not checked properly.
- Risk: Uses `try_to_vec` and `borrow_mut` without bounds checking — but standard Borsh usage is generally safe.

Function "update_admin":
- Allows current admin to update the admin key.
- Validates caller is current admin via `admin_id` check.
- Updates timestamp using Clock sysvar.
- Risk: No time-based or multi-sig delay for admin change — immediate effect could be risky.
- Relies on `admin_bump` to derive correct PDA — assumes correct bump passed.

Function "create_account":
- Creates a user account with 10 governance points.
- Uses PDA derived from "userAccount", user pubkey, and `user_bump`.
- Initializes account via CPI with system program.
- Risk: Fixed 10 governance points — no mechanism to adjust or prevent inflation if exploited.
- No check for whether user already has an account (only checks lamports), so could be front-run.

Function "open_proposal":
- Allows a user to create a new governance proposal.
- Sets proposal duration to 1 hour from current time using Clock sysvar.
- Stores title, description, timestamps, and initializes vote counts.
- Risk: Title is used in PDA derivation — long or duplicate titles could cause issues.
- Risk: No length check on `title` or `description` — could lead to large allocations or DoS.

Function "vote_process":
- Allows a user to vote on a proposal with their full governance weight.
- Uses PDA derived from "vote", user key, proposal key, and `vote_bump`.
- Checks that voting period has not ended.
- Updates proposal vote counts using checked arithmetic.
- Risk: Vote weight is based on current `amount_governance_points` — if points change post-vote, no locking mechanism.
- Risk: Vote record is created after vote — no prevention of double voting via account check (relies on PDA uniqueness).

Function "manage_governance_points":
- Allows admin to add or subtract governance points from a user.
- Uses unchecked subtraction when `instruction` is false (`amount` is subtracted directly).
- Risk: Subtraction can underflow if `amount > user.amount_governance_points`.
- Only checked addition uses `checked_add`; subtraction uses raw `-` operator.
- Critical vulnerability: Potential for underflow leading to large `u64` values.

Function "execute_instruction":
- Handles CPI to Vault program for vault creation, deposit, or withdraw.
- Performs different PDA checks based on `variant_instr` (0,1,2).
- For `variant_instr = 0 or 2`, checks that `user_account_dao` is the admin PDA — but uses `user_bump`, not `admin_bump`.
- Risk: Confuses `user_bump` with `admin_bump` in admin PDA derivation — could allow unauthorized access if bumps are predictable.
- Validates `ix_sysvar` and checks previous instruction was from Vault program — attempts to prevent replay or injection.
- Risk: Previous instruction check is fragile — can be bypassed if CPI order is manipulated.
- Calls `send_create_vault_transaction` or `send_instr_to_vault_transaction` after validation.
- Risk: `id_pubkey` is set to `program_id.clone()` — may not be intended if used as identifier in Vault.

Function "make_decision":
- Allows admin to finalize a proposal after its end time.
- Checks that current time is past `end_time`.
- Marks proposal as executed and logs outcome.
- Risk: No check that proposal hasn't already been executed — could be called multiple times.
- Should set `executed = true` only if not already executed to prevent re-entry.
